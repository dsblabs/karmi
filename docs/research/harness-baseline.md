# Harness baseline: what Claude Code, Codex CLI and pi share, and what must be re-imagined serverlessly

Research note, 2026-08-28. Primary sources only: Claude Code docs (code.claude.com) and Agent SDK docs; Codex docs (developers.openai.com/codex, which now 308-redirects to learn.chatgpt.com) plus the open-source `openai/codex` Rust tree; pi docs and source in `earendil-works/pi` (the `badlogic/pi-mono` URL redirects there). Every claim cites a bracket key; the reference list is in section 5. Anything not verifiable from a primary source is marked "not documented". "Serverless re-imagining" rows are written against the constraints in `docs/research/runtime-comparison.md` [RC]: one SQLite DO per session, hibernation after 10 s idle with in-memory state lost, 5 min CPU per invocation, 128 MB memory, no local filesystem, hibernatable WebSockets, Workflows for long loops, Containers/Sandbox SDK or Dynamic Workers for code execution, remote MCP only. Glossary terms (Framework, Harness, Primitive, Capability, Channel, Scope) follow `CONTEXT.md`.

Terminology note: this document uses "harness" for the running loop machinery (CONTEXT.md sense) and "Harness" capitalised when proposing what karmi must implement.

## 1. Summary

Baseline features every one of the three shares:

1. **The loop is model → tool calls → tool results → model, until a response has no tool calls.** Claude Code counts each cycle as a "turn" [SDK-loop]; Codex calls it a turn made of items [CX-appserver]; pi emits `turn_start`/`turn_end` per LLM call + tool batch [PI-core].
2. **Tools are declared as name + description + JSON-schema parameters and return typed content blocks** (`text`, `image`) with an `isError` flag [SDK-tools][PI-core][CX-protocol].
3. **Parallel tool execution is gated per tool**: read-only/parallel-safe tools run concurrently, mutating ones serialise [SDK-loop][CX-parallel][PI-core].
4. **Token-level streaming of assistant text, thinking and partial tool-call JSON** to the UI, with a separate "complete message" event after the stream [SDK-stream-out][CX-appserver][PI-json].
5. **Automatic context compaction**: summarise older history when a token threshold is crossed, keep a recent tail, re-inject standing instructions [CC-ctx][CX-config][PI-compact].
6. **Tool output truncation with spill-to-disk**: Claude Code ~30,000 chars inline [CC-tools]; Codex `tool_output_token_limit` and hook output spill above ~2,500 tokens [CX-core-config][CX-hooks]; pi 50 KB / 2,000 lines with `fullOutputPath` [PI-ext].
7. **A pre-tool gate that can allow, deny, or rewrite the tool input**: `PreToolUse` hooks with `permissionDecision`/`updatedInput` [CC-hooks][CX-hooks]; pi's `tool_call` event with mutable `event.input` and `{ block: true }` [PI-ext].
8. **Lifecycle hooks around session start/end, prompt submit, tool use, stop and compaction**, configured out-of-band from the prompt [CC-hooks][CX-hooks][PI-ext].
9. **Skills as `SKILL.md` folders with `name`/`description` frontmatter, progressively disclosed** (only names/descriptions in the system prompt; body loaded on invocation) [CC-skills][CX-skills][PI-skills].
10. **Project instruction files discovered by walking the directory tree** (`CLAUDE.md`, `AGENTS.md`) [CC-ctx][CX-agentsmd][PI-agent].
11. **Append-only JSONL session transcripts on local disk, keyed by working directory, with `--continue`/`--resume` and forking** [CC-sessions][CX-rollout][PI-session].
12. **Image input by paste, drag, path or `-i` flag, sent as base64 blocks; tools may return image blocks** [CC-workflows][CX-cli][PI-rpc][SDK-tools].
13. **A machine-readable event protocol for embedding**: Claude Code `stream-json` / Agent SDK messages [CC-headless]; Codex app-server JSON-RPC and `codex exec --json` [CX-appserver][CX-exec-events]; pi `--mode rpc` / `--mode json` [PI-rpc][PI-json].
14. **Steering / follow-up queues**: user messages queued mid-turn and delivered at the next model call [SDK-stream-in][CX-appserver][PI-core].

Where they meaningfully diverge:

- **Permissions**: Claude Code has six modes plus rule syntax plus an optional OS sandbox and a classifier model [CC-modes][CC-perms]; Codex has `approval_policy` x `sandbox_mode` with an always-on OS sandbox [CX-sandbox]; pi has no permission prompts and no sandbox by design, only "project trust" for loading config, and expects the OS/container to isolate [PI-security].
- **Sub-agents**: Claude Code and Codex ship them as first-class tools with definition files [CC-subagents][CX-subagents]; pi deliberately ships none and points at extensions [PI-agent].
- **MCP**: Claude Code and Codex are MCP clients with stdio + HTTP transports [CC-mcp][CX-config]; pi excludes MCP from core [PI-agent].
- **Extension model**: Claude Code = markdown/JSON config + subprocess hooks + plugins [CC-plugins]; Codex = TOML config + JSON hooks + plugins [CX-config][CX-plugins]; pi = in-process TypeScript modules with a full event/tool/UI API [PI-ext].
- **Session structure**: pi stores a tree (`id`/`parentId`) and branches in place [PI-session]; Claude Code and Codex store linear transcripts and fork by copying to a new id [CC-sessions][CX-appserver].
- **Compaction implementation**: Codex can run compaction server-side via the Responses API (`compact_remote.rs`) [CX-compact-remote]; the other two summarise client-side.

## 2. Per-dimension sections

### 2.1 Agent loop

| Harness | How it works |
|---|---|
| Claude Code | `query()` yields `SystemMessage(init)` → `AssistantMessage` (text + `tool_use` blocks) → `UserMessage` (tool results) → … → final `AssistantMessage` with no tool calls → `ResultMessage` with subtype `success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, `error_max_structured_output_retries`; `maxTurns` counts tool-use turns only; `maxBudgetUsd` covers subagents [SDK-loop]. Streaming input mode keeps the process alive across prompts and supports queued messages and `interrupt()` [SDK-stream-in]. `Stop` hooks can refuse to let the loop end (exit 2) and `PostToolBatch` can stop it before the next model call [CC-hooks]. |
| Codex CLI | Thread → turn → items. `turn/start` runs until the model stops or `turn/interrupt`; `turn/steer` appends input to an in-flight turn; `turn/completed` carries token usage [CX-appserver]. Core `Op` enum includes `TurnInput`, `Interrupt`, `ExecApproval`, `PatchApproval`, `Compact`, `Review`, `ThreadRollback`, `Shutdown` [CX-protocol]. Non-interactive: `codex exec --json` emits `thread.started`, `turn.started`, `item.started/updated/completed`, `turn.completed`, `turn.failed`, `error` [CX-exec-events]. |
| pi | `Agent` class (pi-agent-core): `prompt()`/`continue()`, `steer()`/`followUp()`, `abort()`, `waitForIdle()`; events `agent_start/end`, `turn_start/end`, `message_start/update/end`, `tool_execution_start/update/end`; `transformContext()` then `convertToLlm()` run before every model call; `shouldStopAfterTurn` callback; steering messages delivered after the current tool batch, follow-ups only when no tool calls remain [PI-core]. Low-level `agentLoop()`/`agentLoopContinue()` expose the raw stream [PI-core]. |
| **Serverless re-imagining** | The loop must be a **state machine persisted in DO SQLite, not a process**: each model call and each tool batch is a step whose inputs/outputs are rows, so a hibernation or 5 min CPU cap between steps loses nothing [RC §6.3]. Interactive turns run inside the DO; unattended multi-hour loops run as a Workflow with `step.do` per model turn / tool call [RC §6.5]. `interrupt`, `steer` and `followUp` become rows in a queue table checked at step boundaries (pi's steering semantics map directly). Result subtypes and turn/budget caps carry over as-is. |

Carries over unchanged: turn/step semantics, stop-reason and result subtypes, `maxTurns`/budget caps, steering vs follow-up queue semantics, `transformContext`/`convertToLlm` pipeline stages.
Tied to local FS/terminal, must be re-imagined: the loop as a long-lived OS process with in-memory state; `interrupt()` as a signal to a process; SIGTERM/SIGINT handling [CC-headless].

### 2.2 Tool-call protocol

| Harness | Declaration | Parallelism | Result shape | Errors |
|---|---|---|---|---|
| Claude Code | Built-ins are fixed (`Read`, `Edit`, `Write`, `Glob`, `Grep`, `Bash`, `WebFetch`, `WebSearch`, `Agent`, `Skill`, `ToolSearch`, `AskUserQuestion`, `Monitor`, `SendMessage`, `TaskCreate/Update` …) [CC-tools]. Custom tools are in-process MCP servers: `tool(name, description, zodSchema, handler, {annotations})` wrapped by `createSdkMcpServer`, exposed as `mcp__<server>__<tool>` [SDK-tools]. MCP tool definitions are deferred by default and loaded via `ToolSearch` [CC-mcp]. | Read-only tools (and MCP tools with `readOnlyHint: true`) run concurrently; `Edit`/`Write`/`Bash` run sequentially; custom tools default to sequential [SDK-loop][SDK-tools]. | MCP `CallToolResult`: `content: [{type: text|image|audio|resource|resource_link}]`, optional `structuredContent`, `isError` [SDK-tools]. | Uncaught handler exceptions become error results; `isError: true` lets the tool compose the message; a denied tool returns a rejection message as the tool result [SDK-tools][SDK-loop]. |
| Codex CLI | Built-in handlers in `core/src/tools/handlers`: shell/unified exec, `apply_patch`, `view_image`, `mcp`, `mcp_resource`, `plan`, `request_permissions`, `request_user_input`, `tool_search`, `send_user_message_async`, `sleep`, `get_context_remaining`, `new_context_window`, `dynamic` [CX-handlers]. MCP tools declared in `[mcp_servers.<id>]` with `enabled_tools`/`disabled_tools`, `tool_timeout_sec` (default 60) [CX-config]. `features.shell_tool`, `features.unified_exec` toggle built-ins [CX-config]. Dynamic tools via app-server `DynamicToolCallRequest` (experimental) [CX-protocol]. | Runtime admits calls through a `parallel_execution` RwLock: `router.tool_supports_parallel(&call)` decides shared vs exclusive [CX-parallel]. | `FunctionCallOutputPayload` with `ContentItem::OutputText`/`InputImage` [CX-protocol]; exec items carry `status: completed|failed|declined`, `exitCode`, output [CX-exec-events]. Output truncated by `TruncationPolicy::Bytes|Tokens` (middle truncation) under `tool_output_token_limit` [CX-trunc][CX-core-config]. | `FunctionCallError` → `failure_response`; aborted calls return an "aborted after N s" message [CX-parallel]. |
| pi | `AgentTool { name, description, parameters: TypeBox, execute(toolCallId, params, signal, onUpdate, ctx), executionMode? }` registered via `pi.registerTool()`; `promptSnippet`/`promptGuidelines` add to the system prompt; built-ins (`read`, `write`, `edit`, `bash`, `grep`, `find`, `ls`, `powershell`) can be overridden or given remote `operations` [PI-core][PI-ext]. | Default `parallel`: preflight sequentially, execute concurrently, persist results in assistant source order; any tool with `executionMode: "sequential"` forces the whole batch sequential [PI-core]. | `{ content: [{type:"text"}|{type:"image", data, mimeType}], details?, usage?, isError }`; `onUpdate` streams partial results; tools MUST truncate (50 KB / 2,000 lines, `truncateHead`/`truncateTail`) [PI-core][PI-ext]. | Tools throw; the agent converts to `isError: true` results [PI-core]. |
| **Serverless re-imagining** | Tool definitions are **code registered at Worker deploy time** (pi's `registerTool` shape, JSON-schema parameters, `readOnly` flag) plus remote MCP servers discovered per Scope [RC §3]. Tool execution is a step: results go to SQLite immediately (rows ≤ 2 MB; larger to R2 + pointer) so a hibernation between tool end and the next model call is safe [RC §6.1]. Parallel batches are `Promise.all` inside one invocation, bounded by the 6 concurrent outbound connections and 5 min CPU [RC §2]. `Read`/`Edit`/`Bash`/`Glob`/`Grep` are not built-ins; they become a Capability backed by a Sandbox (Container or Dynamic Worker) whose disk is ephemeral [RC §6.7]. |

Carries over unchanged: name/description/schema declaration, `content[]` + `isError` result shape, `readOnly`-gated parallelism, `onUpdate` partial results, middle/head/tail truncation policies, `mcp__server__tool` naming, deferred tool loading (`ToolSearch`).
Tied to local FS/terminal, must be re-imagined: every filesystem/shell built-in; `Bash` timeouts that background a process (`BASH_DEFAULT_TIMEOUT_MS` 2 min, backgrounded at timeout) [CC-tools]; spill-to-file paths (`fullOutputPath`); `PI_SESSION_FILE`-style env vars handed to tools [PI-agent]; stdio MCP servers.

### 2.3 Streaming

| Harness | Model → UI events | Partial tool input | Stream resumption |
|---|---|---|---|
| Claude Code | `--output-format stream-json --include-partial-messages` / SDK `includePartialMessages` yields `stream_event` wrapping raw Anthropic events (`message_start`, `content_block_start`, `content_block_delta` with `text_delta`/`input_json_delta`/thinking, `content_block_stop`, `message_delta`, `message_stop`); then a complete `assistant` message; `parent_tool_use_id` tags subagent messages; `system/api_retry` events surface retries [SDK-stream-out][CC-headless]. Subagent token deltas are not forwarded [SDK-stream-out]. | `input_json_delta.partial_json` accumulated by the client [SDK-stream-out]. | Not documented. Sessions resume from the transcript, not from a stream position. |
| Codex CLI | app-server notifications: `item/started`, `item/agentMessage/delta`, `item/reasoning/*` deltas, `item/commandExecution/outputDelta`, `item/completed`, `turn/completed`, `thread/tokenUsage/updated`; clients can `optOutNotificationMethods` [CX-appserver]. Core `EventMsg` has `AgentMessageContentDelta`, `ReasoningContentDelta`, `ExecCommandOutputDelta`, `PlanDelta`, `StreamError` [CX-protocol]. | `item/started` shows the pending item; input deltas for tool calls are not documented as a separate delta type. | `thread/resume` reconstructs turn history (`excludeTurns` + `thread/turns/list`/`thread/items/list` for paginated threads); `thread/tokenUsage/updated` is replayed on cold resume; only one app-server process may hold a thread for writing [CX-appserver]. No mid-turn stream reattach documented. |
| pi | `message_update` carries `assistantMessageEvent` of type `text_delta`, `thinking_delta`, `toolcall_delta`, `toolcall_start`; `tool_execution_update` carries `partialResult`; `--mode json` omits cumulative `partial` snapshots [PI-json][PI-rpc]. | `toolcall_delta` events [PI-json]. | Not documented; RPC is a stdin/stdout pipe. |
| **Serverless re-imagining** | Events are **written to a SQLite event table with a monotonic id and fanned out over hibernatable WebSockets** owned by the session DO (or SSE from a Worker proxy) [RC §6.4]. Reconnect = client sends last-seen id, DO replays; deploys disconnect all sockets so this is mandatory [RC §6.11]. Model streaming uses HTTP `fetch` (outbound WebSockets never hibernate and are billed for duration) [RC §6.4]. Event vocabulary: adopt pi/Codex's three-level shape (turn → message/item → delta) since it is provider-neutral, and wrap raw provider events like Claude Code does only as an opt-in. |

Carries over unchanged: the event vocabulary (turn/item start–delta–complete), `parent_tool_use_id`-style attribution, token-usage events, retry events, tool-output deltas.
Tied to local FS/terminal, must be re-imagined: stdout/stdin JSONL pipes as the transport; TTY rendering; the absence of any resumption story (all three assume an unbroken pipe).

### 2.4 Context management and compaction

| Harness | Trigger | What is kept | Micro-compaction of tool results |
|---|---|---|---|
| Claude Code | Auto-compacts when the conversation reaches the model's context limit (200K boundary for 200K models; Sonnet 5 at ~967K of 1M); window set by `/autocompact 500k`, `--autocompact`, `autoCompactWindow` setting or `CLAUDE_CODE_AUTO_COMPACT_WINDOW` (100K–1M); `DISABLE_COMPACT` turns it off; `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` applies to subagents [CC-model][CC-subagents]. `/compact [instructions]`; CLAUDE.md "compact instructions" section honoured [CC-costs][SDK-loop]. `PreCompact`/`PostCompact` hooks with `manual|auto` matcher; `PreCompact` exit 2 blocks compaction [CC-hooks]. Emits `system/compact_boundary` with `compactMetadata.trigger` and `preTokens` [CC-subagents]. | Structured summary + most recent exchanges + up to five recently read/edited files re-read (files >5,000 tokens as path references) + CLAUDE.md and rules reloaded + invoked skill bodies re-injected (truncated to a per-skill cap) + `SessionStart` hooks with `compact` matcher re-run [CC-ctx][CC-sessions]. "Resume from summary" dialog on stale >100K sessions [CC-sessions]. | Not documented as a separate mechanism; MCP tool schemas are deferred to save context (`ToolSearch`) [CC-mcp]. |
| Codex CLI | `model_auto_compact_token_limit` (scope `total` or `body_after_prefix`), `model_context_window` [CX-config][CX-core-config]. `/compact` in the TUI; `thread/compact/start` in app-server [CX-cli][CX-appserver]. Hooks `PreCompact`/`PostCompact` with `manual|auto` matcher; `PreCompact` can prevent compaction [CX-hooks]. Emits `ContextCompacted` event and `contextCompaction` item [CX-protocol][CX-appserver-doc]. | `build_compacted_history`: summary (`SUMMARIZATION_PROMPT`, `SUMMARY_PREFIX`) plus the user messages, walking newest-first under `COMPACT_USER_MESSAGE_MAX_TOKENS = 20_000` with per-message truncation; initial context (AGENTS.md etc.) re-injected before the last real user message or the summary [CX-compact]. Remote variant runs compaction through the Responses API (`CompactionImplementation::ResponsesCompact`) [CX-compact-remote]. | `tool_output_token_limit` truncates each tool output at ingestion; `get_context_remaining` and `new_context_window` tools let the model manage context itself [CX-core-config][CX-handlers]. |
| pi | `contextTokens > contextWindow - reserveTokens` (reserve default 16,384), checked after tool results are appended and before the next assistant response, before a new prompt, and after a run ends; also on context-overflow error recovery; `/compact [instructions]`; settings `compaction.enabled|reserveTokens|keepRecentTokens` [PI-compact][PI-settings]. Hooks `session_before_compact` (can cancel or supply a custom summary), `session_compact`, `session_compact_failed` [PI-ext]. | Walk back until `keepRecentTokens` (20,000) at a turn boundary (never inside a tool-call/result pair); "split turn" yields two merged summaries; `CompactionEntry { summary, firstKeptEntryId, tokensBefore }` appended to the tree; context rebuilt as system + summary + entries from `firstKeptEntryId`; file operations tracked cumulatively across summaries; branch switches can attach a `branch_summary` [PI-compact][PI-session]. | Per-tool truncation only (50 KB / 2,000 lines) [PI-ext]. |
| **Serverless re-imagining** | Compaction is a **step of the loop with its own CPU budget** (summarising a large context is one model call, I/O-bound, fine under 5 min) that writes a compaction row and a `firstKeptEntryId` pointer; context is rebuilt from SQLite on every wake anyway, so pi's "rebuild from pointer" design is the natural fit [RC §6.3]. Thresholds (`reserveTokens`, `keepRecentTokens`, absolute window) are per-agent configuration. Token counting for the threshold must be cheap (estimate or provider `usage` from the last call) because JSON parsing of large contexts costs CPU [RC §6.2]. "Re-read five recent files" has no meaning without a filesystem; the analogue is re-attaching the last N artifacts stored in R2. |

Carries over unchanged: threshold-based auto-compaction, manual compaction with focus instructions, pre/post-compaction hooks with veto, turn-boundary cut rules, summary + kept-tail structure, re-injection of standing instructions, compaction boundary events, provider-side compaction as an optional path.
Tied to local FS/terminal, must be re-imagined: re-reading recently touched files; CLAUDE.md/AGENTS.md discovery by directory walk (becomes a dynamic-prompt Primitive); `PI_SESSION_FILE`/`transcript_path` handed to hooks.

### 2.5 Permission / approval model

| Harness | Modes | Rules | Per-tool prompts | Sandboxing |
|---|---|---|---|---|
| Claude Code | `default` (Manual), `acceptEdits`, `plan`, `auto` (classifier model reviews actions; falls back to prompting after 3 consecutive / 20 total blocks), `dontAsk`, `bypassPermissions`; `defaultMode` in settings; `Shift+Tab` cycles; `disableBypassPermissionsMode`/`disableAutoMode` in managed settings [CC-modes][CC-perms]. | Codex CLI | `approval_policy = untrusted | on-request | on-failure | never | { granular = {...} }` and `sandbox_mode = read-only | workspace-write | danger-full-access`; `--full-auto`, `--yolo`/`--dangerously-bypass-approvals-and-sandbox`; `approvals_reviewer = user | auto_review` routes approvals to a reviewer agent [CX-config][CX-sandbox][CX-cli]. | `projects.<path>.trust_level = trusted|untrusted` gates project config; execpolicy rules (`execpolicy` crate) and `acceptWithExecpolicyAmendment` persist command allowances; network policy amendments per host [CX-config][CX-appserver]. | Server-initiated JSON-RPC requests: `item/commandExecution/requestApproval` (decisions `accept`, `acceptForSession`, `acceptWithExecpolicyAmendment`, `applyNetworkPolicyAmendment`, `decline`, `cancel`), `item/fileChange/requestApproval`, `item/permissions/requestApproval` (grant subset, `scope: session|turn`), `tool/requestUserInput`, MCP `mcpServer/elicitation/request` [CX-appserver]. Core `ReviewDecision`: `Approved`, `ApprovedForSession`, `Denied`, `TimedOut`, `Abort` … [CX-protocol]. | Always-on OS sandbox: macOS Seatbelt, Linux bubblewrap (user namespaces + seccomp; Landlock per security page), Windows sandbox; `.git` and `.codex` protected; network blocked by default in `workspace-write` unless `network_access = true`; `writable_roots`, `exclude_tmpdir_env_var`, `exclude_slash_tmp`; sandbox failure escalates to an approval under `on-failure` [CX-sandbox][CX-config]. |
| pi | None. "Pi deliberately excludes … permission popups" [PI-agent]. Only **project trust** (`defaultProjectTrust = ask|always|never`, `~/.pi/agent/trust.json`, `--approve`/`--no-approve`) which gates loading `.pi/` resources, not tool execution [PI-security]. | None built in; extensions implement gates in `tool_call` (`{ block: true, reason, terminate }`) and can prompt via `ctx.ui.confirm` [PI-ext]. | Extension-provided via `ctx.ui.select|confirm|input`; in RPC mode surfaced as `extension_ui_request`/`extension_ui_response` [PI-ext][PI-rpc]. | None. "Real isolation needs to come from the operating system or a virtualization/container boundary"; documented patterns: run pi in a container, or route built-in tool execution into a micro-VM via `operations` [PI-security][PI-ext]. |
| **Serverless re-imagining** | Modes and allow/ask/deny rules are pure data and carry over. The **prompt itself becomes a durable pending-approval row** answered by a Channel (Codex's server-initiated request with `acceptForSession` scope is the right shape); interactive waits stay in the DO, long waits use Workflow `waitForEvent` (24 h default, up to 365 d) [RC §6.5]. The sandbox question inverts: the harness has no host to protect, so "sandbox" means **which Capability backend runs code** (Dynamic Worker with `globalOutbound: null` vs Container) and per-Scope egress via an outbound Worker [RC §6.7–6.8]. Classifier-based auto mode is a model call and carries over if a Framework user wants it. |

Carries over unchanged: mode vocabulary, deny→ask→allow rule evaluation, tool-name and parameter-scoped rule syntax, per-session grants (`acceptForSession`), hook-driven auto-decisions, `AskUserQuestion`/`requestUserInput`, trust levels for loading config.
Tied to local FS/terminal, must be re-imagined: path-based rules (`Read(./.env)`, `writable_roots`) which need a virtual filesystem to mean anything; Seatbelt/bubblewrap/Landlock; `.git`/`.codex` protection; interactive TTY prompts; `Shift+Tab`.

## 3. Baseline vs primitive split (proposed)

| Item | Cut | One-line rationale |
|---|---|---|
| Loop state machine (model call → tool batch → results → repeat; turn/step boundaries; stop reasons; result subtypes) | **Harness** | All three implement the identical cycle; karmi must implement it once, persisted per step so hibernation and CPU caps are invisible. |
| Steering / follow-up / interrupt queues | Harness | Present in all three with the same delivery semantics (after current tool batch vs after completion); purely loop plumbing. |
| Event stream with monotonic ids, WS fan-out, replay on reconnect | Harness | Streaming vocabulary is shared; resumption is absent locally and mandatory serverlessly (deploys drop sockets). |
| Tool registry, schema validation, parallel-vs-sequential gate, result normalisation and truncation/spill | Harness | Identical across the three; the gate (`readOnly`) and `content[]/isError` shape are the protocol. |
| Compaction engine (threshold check, cut-point rules, summary step, pointer to kept tail, re-injection) | Harness | Same algorithm in all three; the summary prompt and thresholds are configuration. |
| Permission evaluator (modes, deny→ask→allow, per-session grants, pending-approval rows) | Harness | Rule semantics are data; the evaluator and the durable "waiting for approval" state are loop machinery. |
| Hook dispatcher (event bus, matchers, decision merging, timeouts) | Harness | The bus is shared; what hooks do is user code. |
| Sub-agent spawn/await/message plumbing (child DO lifecycle, result callback, depth/concurrency caps) | Harness | Two of three ship it; the third says "build it on registerTool + exec", which is exactly the plumbing karmi should own. |
| Session store (append-only tree, fork with id rewrite, list/archive, PITR, export in `SessionStore` shape) | Harness | Persistence is the DO's reason to exist; the schema is shared across the three. |

## 4. Open questions for the primitives grilling

1. **Is a sub-agent a Primitive or just an Agent invoked as a Tool?** Claude Code and Codex give it a separate definition file and separate caps; pi refuses the concept. The proposed cut says "Agent referenced from a tool list", which leaves fork-with-inherited-context (Claude Code `/subtask`, Codex `thread/fork`) as a Harness operation rather than a definition field. Does karmi need fork-style sub-agents in v0 at all?
2. **Where does the hook live: on the Agent, on the Scope, or on the session?** Claude Code layers user/project/local/managed/plugin/frontmatter; Codex layers user/project/plugin/managed; pi has global/project extensions. Serverlessly there is no directory hierarchy, so the layering must be explicit (Scope defaults → Agent → per-session overrides?).
3. **Tree vs linear transcript.** pi's `id`/`parentId` tree makes compaction and branching pointer operations; Claude Code/Codex copy files. Adopting the tree changes the `SessionStore` export shape (subpath-free) and complicates "replay from event id". Which one is the source of truth: the message tree or the event log?
4. **Compaction ownership.** Codex can compact server-side via the Responses API; Anthropic's SDK compacts client-side. Should compaction be pluggable per provider (a Capability of the model gateway) or always a Harness step?
5. **Permission rules without a filesystem.** `Read(./.env)`, `writable_roots`, `.git` protection all presume paths. Are path rules a property of the Sandbox Capability (and therefore absent for agents without it), or a generic "resource pattern" rule the Harness evaluates for any tool?
6. **Auto/classifier mode.** Claude Code's classifier is model-driven and not configurable in detail; Codex has `approvals_reviewer = auto_review`. Is a "reviewer agent" a Primitive users compose, or a Harness feature?
7. **Hook handler types.** Claude Code supports `command|http|mcp_tool|prompt|agent`; Codex only `command|mcp_tool`. In karmi `command` disappears; do `prompt`/`agent` handlers (a model deciding a hook outcome) belong in v0?
8. **Steering delivery mode** (`one-at-a-time` vs `all`) and follow-up queues: pi exposes them as settings, Claude Code and Codex fix the behaviour. Configurable per Agent or fixed?
9. **Tool output limits.** 30,000 chars (Claude Code), token budget (Codex), 50 KB / 2,000 lines (pi). Per-tool or per-Agent setting, and does the spill target (R2) count as a Capability?
10. **Skills-as-commands.** Claude Code merged `.claude/commands` into skills; pi keeps prompt templates separate; Codex has neither prompt templates (not documented) nor user commands beyond `$skill`. Does karmi need a separate "prompt template" Primitive or is a Skill with `disable-model-invocation: true` sufficient?
11. **Not verified from primary sources:** Codex sub-agent nesting depth limit; Codex mid-turn stream reattach; Codex cross-machine session portability; pi's max concurrent tool executions; whether the learn.chatgpt.com redirect target is the canonical Codex docs host (the 308 came from developers.openai.com, and github.com/openai/codex/docs still links developers.openai.com).

## 1. Transports

**Spec state.** Protocol versions are `YYYY-MM-DD` strings marking the last backwards-incompatible change; the revisions are 2024-11-05, 2025-03-26, 2025-06-18, 2025-11-25 and 2026-07-28, and "the current protocol version is 2026-07-28" [MCP-versioning]. Two standard transports exist: stdio and Streamable HTTP [MCP-transports-2025]. Streamable HTTP "was introduced in protocol version 2025-03-26 as a replacement for the HTTP+SSE transport from protocol version 2024-11-05"; HTTP+SSE "has been deprecated since protocol version 2025-03-26", is now formally Deprecated under the feature-lifecycle policy (SEP-2596) and is "eligible for removal … three months after SEP-2596 reaches Final" [MCP-http-2026][MCP-deprecated].

**What 2026-07-28 changed** (all from [MCP-changelog], transport detail from [MCP-http-2026]): (1) protocol-level sessions and the `Mcp-Session-Id` header are removed; servers needing state return explicit handles as ordinary tool arguments (SEP-2567); (2) the `initialize`/`notifications/initialized` handshake is removed; every request carries `_meta["io.modelcontextprotocol/protocolVersion"]`, `…/clientCapabilities` and (SHOULD) `…/clientInfo`; mismatches return `UnsupportedProtocolVersionError` (-32022); (3) `server/discover` is a mandatory RPC advertising supported versions, capabilities and identity; (4) the HTTP GET stream is replaced by `subscriptions/listen`, a long-lived POST whose response stream carries only the opted-in notifications (`toolsListChanged`, …); (5) `ping`, `logging/setLevel`, roots list-changed removed; (6) tasks moved to an extension; (7) server→client requests (sampling, elicitation, roots) are replaced by Multi Round-Trip Requests: the server returns `resultType: "input_required"` with `inputRequests`, the client retries the original call with `inputResponses` and a new request id (SEP-2322); (8) every result carries `resultType`; (9) SSE resumability (`Last-Event-ID`) is removed — "A broken response stream loses the in-flight request; clients MUST re-issue it". Minor: `Mcp-Method` and `Mcp-Name` headers are REQUIRED on POSTs and `x-mcp-header` mirrors tool parameters into `Mcp-Param-*` headers (SEP-2243); `tools/list` and friends MUST carry `ttlMs` and `cacheScope` (SEP-2549); servers SHOULD return tools in deterministic order "to improve LLM prompt cache hit rates"; Sampling, Roots and Logging are Deprecated (earliest removal 2027-07-28); Dynamic Client Registration is Deprecated in favour of Client ID Metadata Documents [MCP-changelog][MCP-deprecated].

**Legacy era (2025-03-26 … 2025-11-25).** Single MCP endpoint supporting POST and GET; POST returns `application/json` or `text/event-stream`; server MAY mint `Mcp-Session-Id` on the `InitializeResult` and clients MUST echo it on every request; 404 on a session id means "start a new session by sending a new InitializeRequest"; DELETE terminates; `MCP-Protocol-Version` header MUST be sent on subsequent requests; servers MUST validate `Origin` [MCP-transports-2025]. A 2026 client must be **dual-era**: attempt a modern request, and on `400` inspect the body — a recognised modern JSON-RPC error means "modern server, retry with a supported version"; anything else means fall back to `initialize`, and from a `4xx` without a modern error body fall further back to the HTTP+SSE GET probe. The era verdict "is a property of the server" and clients SHOULD cache it per origin and MAY persist it [MCP-versioning-2026][MCP-http-2026].

**`@modelcontextprotocol/sdk` 1.30.0** (2026-07-27) [MCP-sdk-npm]: `engines.node >=18`; runtime deps include `express`, `hono`, `@hono/node-server`, `cors`, `express-rate-limit`, `raw-body`, `ajv`, `ajv-formats`, `zod ^3.25 || ^4`, `zod-to-json-schema`, `jose`, `eventsource`, `eventsource-parser`, `cross-spawn`, `pkce-challenge`; exports `./client`, `./validation/ajv`, `./validation/cfworker`, `./experimental/tasks`. It implements the 2025 era only (no `server/discover`, no MRTR) — the v2 line "implement[s] the 2026-07-28 MCP spec" [MCP-ts-readme].

**`@modelcontextprotocol/client` 2.0.0** (2026-07-27; betas since 2026-06-30) [MCP-client-npm][MCP-client-pkg]: `engines.node >=20`; runtime deps only `@modelcontextprotocol/core 2.0.0` (zod schemas), `cross-spawn`, `eventsource`, `eventsource-parser`, `jose`, `pkce-challenge`, `zod ^4.2`. Exports: `.`, `./stdio` (kept off the root "to keep the root entry free of process-spawning runtime dependencies"), `./validators/ajv`, `./validators/cf-worker`, and `./_shims` with a **`workerd` export condition** that selects `shimsWorkerd.mjs` [MCP-client-pkg][MCP-client-index]. The workerd shim sets `DefaultJsonSchemaValidator = CfWorkerJsonSchemaValidator` (`@cfworker/json-schema`, bundled) and calls `preloadSchemas()` at module scope because "isolate platforms like workerd evaluate module scope during deployment/isolate warm-up, outside any request's billed CPU" [MCP-client-shims]. AJV is not usable on Workers: it "compiles schemas with `new Function`, which Workers disallows, failing discovery with 'Code generation from strings disallowed for this context'" [Agents-changelog]. `StreamableHTTPClientTransport` is fetch-based (`fetch?: FetchLike` option; only a type import from `node:stream/web`) and parses SSE with `eventsource-parser/stream`; `SSEClientTransport` uses the `eventsource` npm package (a WHATWG EventSource over fetch, dep `eventsource-parser`); `jose` is `await import`ed only for `private_key_jwt` [MCP-client-http][MCP-client-sse][MCP-client-authext]. Node built-ins appear only in the stdio transport (`node:child_process`, `node:stream`, `node:process`) [MCP-client-grep]. Workers also expose a native `EventSource` (with a `fetcher` option and `EventSource.from(stream)` extension) [W-eventsource], and `nodejs_compat` is on by default for compatibility dates ≥ 2026-08-04 [W-nodejs]. Conclusion: the client 2.x root entry runs in workerd with no polyfills; `cloudflare/agents` runs it in workerd in CI against the official conformance suite [Agents-changelog].

**Client 2.x behaviour that matters to a Harness** [MCP-client-client][MCP-client-vn]: `versionNegotiation` defaults to `'legacy'` ("byte-identical to today's behavior"); `'auto'` probes `server/discover` first and falls back to `initialize`; `{ pin: '2026-07-28' }` fails loudly. `connect(transport, { prior })` adopts a cached era verdict "with zero round trips". `inputRequired.autoFulfill` (default true) answers MRTR `input_required` results through the same `setRequestHandler` handlers and retries. `listTools()` auto-paginates up to `listMaxPages` (default 64). A `responseCacheStore` (default in-memory) honours `ttlMs`/`cacheScope`, keyed by server identity and a `cachePartition` "(e.g. the auth subject)"; `defaultCacheTtlMs` is 0. `callTool` compiles `outputSchema`, requires `structuredContent` when an `outputSchema` exists (unless `isError`) and validates it; `listChanged` handlers auto-open a `subscriptions/listen` stream on modern servers.

## 2. Auth

**Spec (2026-07-28)** [MCP-auth-2026]: authorization is OPTIONAL; when used over HTTP the MCP server is an OAuth 2.1 resource server (draft-ietf-oauth-v2-1-13). Normative client obligations: MUST use RFC 9728 Protected Resource Metadata for AS discovery, parse `WWW-Authenticate` on 401 (`resource_metadata`, and SHOULD-provided `scope`); MUST support both RFC 8414 and OpenID Connect Discovery; MUST implement PKCE; MUST send the RFC 8707 `resource` parameter (canonical server URI) on authorization and token requests; MUST send `Authorization: Bearer` on every request and never in the query string; MUST validate a present `iss` (RFC 9207) before redeeming the code; MUST key persisted client credentials by AS `issuer` and re-register when the AS changes (SEP-2352); SHOULD request only challenged scopes and SHOULD step-up on `403 insufficient_scope` with the union of previous and challenged scopes; refresh tokens MUST be kept confidential and MUST NOT be assumed. Registration priority: pre-registered → **Client ID Metadata Documents** (CIMD, SHOULD; `client_id` is an HTTPS URL with a path; the document MUST contain `client_id`, `client_name`, `redirect_uris`; AS advertises `client_id_metadata_document_supported: true`; "portable across authorization servers") → Dynamic Client Registration (MAY, deprecated, MUST send `application_type`) → prompt the user [MCP-client-reg]. AS MUST validate exact redirect URIs [MCP-auth-2025]. Extensions (enterprise cross-app access etc.) live in `modelcontextprotocol/ext-auth` [MCP-auth-2026].

**SDK `OAuthClientProvider`** [MCP-client-auth]: `redirectUrl`, optional `clientMetadataUrl` (CIMD), `clientMetadata`, optional `state()`, `clientInformation(ctx?)` / `saveClientInformation?(info, ctx?)` and `tokens(ctx?)` / `saveTokens(tokens, ctx?)` where `ctx.issuer` lets providers persist per authorization server, `redirectToAuthorization(url)`, `saveCodeVerifier` / `codeVerifier`, optional `addClientAuthentication`, `validateResourceURL`, `invalidateCredentials(scope)`. The SDK uses the URL-based `client_id` only when the AS metadata advertises `client_id_metadata_document_supported` and `clientMetadataUrl` is set, otherwise falls back to DCR and throws if `saveClientInformation` is missing [MCP-client-auth]. Non-interactive providers (`ClientCredentialsProvider`, `PrivateKeyJwtProvider`, `CrossAppAccessProvider`) are exported for machine-to-machine servers [MCP-client-index].

**Agents SDK `DurableObjectOAuthClientProvider`** [Agents-oauth-src]: `constructor(storage: DurableObjectStorage, clientName, baseRedirectUrl)`; stores everything through the DO KV API under `/{clientName}/{serverId}/{clientId}/client_info/`, `…/token`, `…/code_verifier_challenge/{codeChallenge}` (pending PKCE verifiers), `…/code_verifier/{nonce}` (verifier bound to a state), `/{clientName}/{serverId}/state/{nonce}` and `/{clientName}/{serverId}/oauth_discovery`; `state()` returns `${nonce}.${serverId}` with a 10-minute expiry; `redirectToAuthorization` records the auth URL (surfaced to the caller as `authUrl`) and moves the verifier from the challenge slot to the state slot; `codeVerifier()` reads the verifier for the callback's state through a `node:async_hooks` `AsyncLocalStorage` set by `runWithCodeVerifierState` (so `nodejs_compat` is required); `saveTokens` deletes the discovery state so a later 401 re-reads PRM "so an authorization-server migration can be observed"; `clientMetadata` is `token_endpoint_auth_method: "none"`, grants `authorization_code` + `refresh_token`; `clientMetadataUrl` is not set, so the Agents client registers via DCR. Callback interception lives in `MCPClientManager.onRequest` (a Lifecycle capability hook): `isCallbackRequest` accepts a GET whose `state` parses to a stored server id **and** whose origin+pathname equal the stored `callback_url`; `handleCallbackRequest` validates state, runs `completeAuthorization` inside the verifier ALS, then `establishConnection` and redirects per `configureOAuthCallback` [Agents-mcp-client-src]. The documented default callback URL is `https://{host}/agents/{class}/{instance}/callback`, i.e. the DO name is in the path so `routeAgentRequest` lands on the right object; with a custom `callbackPath` "custom routing is required" [Agents-client-api]. (The docs describe the state format as `{serverId}:{stateValue}`; the source uses `${nonce}.${serverId}` — cite the source.) Server rows persist in `cf_agents_mcp_servers (id, name, server_url, callback_url, client_id, auth_url, server_options)` with `server_options` JSON holding transport `sessionId`/`protocolVersion`, `discoverResult`, retry policy and a one-wake capability seed [Agents-storage-src].

**Where tokens live per Scope — analysis.** `CONTEXT.md` says all secrets/config resolve under Scope, and a Scope typically has many sessions.

- (a) *Per-session DO storage* (the Agents model): simplest, no cross-object calls, and refresh is race-free because a DO is single-threaded. But a user must complete the browser OAuth dance once **per session**, tokens are duplicated N times per Scope, revocation must fan out, and the callback must reach the exact session DO (Agents encodes the DO name in the path). Wrong unit for karmi: consent is a Scope-level fact.
- (b) *Scope-level registry DO*: one `McpRegistry` DO per Scope holding server configs, client information keyed by issuer, tokens, PKCE/state, and the cached tool catalogue. Sessions call it over DO RPC. Single-writer semantics make refresh a serialised critical section — needed because for public clients "authorization servers MUST rotate refresh tokens" [MCP-auth-2025], so two sessions refreshing the same refresh token concurrently would invalidate one another. The callback lands on the registry: one fixed redirect URI (`https://{host}/mcp/oauth/callback`, exact-match registered [MCP-client-reg]) with `state = {scopeId}.{nonce}.{serverId}`; the front Worker parses `state`, forwards to the registry DO for `scopeId`, which validates the nonce like the Agents provider does. Revocation is one `invalidateCredentials` call. Cost: one RPC per token fetch (mitigated by handing sessions a short-lived access token plus its `expires_at`; sessions call back only on expiry or 401).
- (c) *Shared store (KV / D1 / Secrets Store)*: KV is eventually consistent and has no compare-and-swap, so refresh rotation races are real; D1 needs its own locking; Secrets Store is write-only, capped and static (below). None gives a natural mutex; all put the token exchange logic in a stateless Worker where two concurrent callbacks/refreshes can interleave. Reject for OAuth; acceptable for read-only static secrets.

**Static bearer / API-key headers** are the common simple case and need no OAuth machinery: the Agents transport options persist `headers` and `requestInit` per server [Agents-storage-src], and the spec's bearer rule applies equally to static tokens [MCP-auth-2026]. In karmi these are Scope config values resolved at call time; they still belong in the registry DO so they are encrypted at rest with the rest of the Scope's secrets and never copied into session rows.

**Cloudflare Secrets Store** [CF-secrets][CF-secrets-workers][CF-secrets-manage]: account-level, open beta; "there can only be one store per account"; "up to 100 secrets per account"; values ≤ 1024 bytes; "once a secret is added … it can no longer be decrypted or accessed via API or on the dashboard"; bound statically in wrangler (`secrets_store_secrets: [{ binding, store_id, secret_name }]`) and read with `await env.X.get()`. It fits deployer-level secrets (provider API keys, the private key for a `private_key_jwt` CIMD client, an at-rest encryption key for the registry) — not per-Scope, runtime-created OAuth tokens.

**Workers for Platforms** isolation: if a Platform runs per-tenant user Workers, Outbound Workers "sit between your customer's Workers and the public Internet", can allow/deny destinations and "configure authentication to your APIs behind the scenes", parameterised per tenant via `dispatcher.get()` [WfP-outbound]. That is the right place for egress policy in a WfP deployment; karmi v0 runs in one Worker and isolates by DO id, so it is out of scope but the registry design must not preclude it (tokens injected by an outbound Worker would simply replace the registry's bearer).

## 3. Tool discovery and caching

**Protocol facts** [MCP-tools-2026][MCP-caching][MCP-subscriptions]: `tools/list` paginates via `cursor`/`nextCursor`; each page carries its own `ttlMs` and `cacheScope` (`public` | `private`); results MUST NOT vary per connection but MAY vary by the presented authorization; servers SHOULD order tools deterministically; `listChanged: true` servers SHOULD emit `notifications/tools/list_changed`, delivered only to clients holding a `subscriptions/listen` stream with `toolsListChanged: true` (legacy: on the GET stream); a notification invalidates a fresh cache entry; TTL "is a freshness hint, not a guarantee" and clients SHOULD NOT poll on it; clients MAY re-fetch early after "an unexpected error on a tool call indicating the method was not found or the parameters were invalid" and MAY serve stale on fetch failure. Tool fields: `name` (SHOULD be 1–128 chars of `[A-Za-z0-9_.-]`, unique per server; aggregators SHOULD prefix with a server identifier and "SHOULD NOT" rely on `serverInfo.name`), `title`, `description`, `icons`, `inputSchema` (JSON Schema, 2020-12 unless `$schema` says e.g. draft-07; any 2020-12 keyword allowed since SEP-2106; MUST be an object schema, not `null`), `outputSchema`, `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`; "clients MUST consider tool annotations to be untrusted unless they come from trusted servers"), `_meta`. Results: `content[]` of `text` | `image` | `audio` | `resource_link` | `resource`, optional `structuredContent` (any JSON value; SHOULD be mirrored as text), `isError` for execution errors versus JSON-RPC errors for protocol errors ("Clients SHOULD provide tool execution errors to language models"). `x-mcp-header`-annotated parameters MUST be mirrored into `Mcp-Param-*` headers and invalid annotations MUST cause the tool to be dropped from `tools/list` [MCP-http-2026].

**Where to cache.** Holding a `subscriptions/listen` (or legacy GET) stream open means an in-flight outbound fetch, which prevents DO hibernation and is billed as wall time [RC]; the Agents SDK nonetheless re-opens the listen stream on every hibernation restore for servers advertising `listChanged` [Agents-conn-src]. For karmi the catalogue should live in the **registry DO** (SQLite row per server: `tools_json`, `catalog_hash`, `fetched_at`, `ttl_ms`, `cache_scope`, `era`, `discover_result`), refreshed (i) when a session starts a turn and the entry is stale by `ttlMs`, (ii) on a protocol error from `tools/call` (`-32602` unknown tool / invalid params), (iii) on explicit admin action, and never by background polling. Because all sessions in a Scope present the same credential, `cacheScope: "private"` is satisfied by keying the cache per Scope (the SDK's `cachePartition` idea) [MCP-client-client]. `catalog_hash` is what the Harness puts in the session's tool-list version so that a stable catalogue yields a stable Anthropic `tools` prefix (tool definition changes invalidate the whole prompt cache: "tools → system → messages") [AN-caching].

**Schema conversion.** Anthropic `input_schema` is "a JSON Schema object" taken verbatim, name regex `^[a-zA-Z0-9_-]{1,64}$` [AN-define-tools]; `tool_result.content` may be a string or `text` | `image` | `document` | `search_result` blocks with `is_error` [AN-handle-tools]. The AI SDK accepts raw JSON Schema through `jsonSchema(schema, { validate })` "as an alternative to using Zod schemas" [AI-jsonschema]. The Agents SDK instead converts with zod 4's `z.fromJSONSchema` and **skips tools whose schema fails conversion** [Agents-mcp-client-src] — a lossy path karmi should not copy. Validation on workerd must use `@cfworker/json-schema` (the client's workerd default; Agents adds a draft-07 fallback for `$schema: draft-07`) [MCP-client-shims][Agents-runtime-src].

**Elicitation and sampling.** In 2026-07-28 both arrive as MRTR `input_required` results, not as inbound requests; the SDK auto-fulfils them only through registered handlers [MCP-elicitation][MCP-client-client]. Clients declare `elicitation: { form?, url? }` per request and "Servers MUST NOT send elicitation requests with modes that are not supported by the client"; URL-mode clients MUST show the full URL and obtain explicit consent [MCP-elicitation]. Sampling is Deprecated ("integrate directly with LLM provider APIs") [MCP-sampling][MCP-deprecated]. v0 decision: advertise **no** elicitation and no sampling capability; set `inputRequired.autoFulfill: false` and surface an `input_required` result as an `isError` tool result explaining that the server needs interactive input. URL-mode elicitation is a Channel concern (a human must click) and is deferred; sampling is never implemented.

## 4. Connection lifetime in a DO

In the 2026 era "the client sends every JSON-RPC request or notification as its own HTTP POST" and there is no session, so a `Client` object holds only in-memory conveniences: the era verdict, the `DiscoverResult`, server capabilities, the response cache and any open `listen` stream [MCP-http-2026][MCP-client-client]. In the legacy era the `Mcp-Session-Id` is the only durable thing; the SDK accepts `sessionId` + `protocolVersion` in the transport options to resume, and a 404 on a stale id means re-`initialize` [MCP-transports-2025][MCP-client-http]. The Agents SDK persists `sessionId`, `protocolVersion` and `discoverResult` per server and, on `onStart` after hibernation, rebuilds every `Client`, reconnects with retry, re-runs discovery when capabilities are unknown, re-opens the listen subscription, and exposes `waitForConnections({ timeout })` "before calling getAITools() after the agent wakes from hibernation"; a restored session that gets 404 is reported as `stale-session` and re-initialised without the id [Agents-mcp-client-src][Agents-conn-src][Agents-storage-src].

**Runtime limits** [W-limits][DO-limits][RC]: "Each Worker invocation can have up to six connections simultaneously waiting for response headers" (a seventh is queued until headers arrive; after headers a connection no longer counts); DOs have the same six-connection limit; 50 subrequests/invocation free, 10,000 paid; "There is no set time limit on individual subrequests"; DO wall time is unlimited while the caller is connected, CPU 30 s default up to 5 min; a DO hibernates after ~10 s idle only if it has no in-flight fetch, otherwise it is evicted after 70–140 s, and "in-memory state is not preserved across eviction or hibernation" [DO-memory][RC]. Implications: a permanently open listen stream per server is the wrong shape (it is an open connection waiting for the SSE stream to end, keeps the object out of hibernation, and its state is lost on eviction anyway); a `tools/call` that returns SSE progress notifications is fine (headers arrive immediately). Parallel tool calls in one turn must be bounded by the six-connection window.

**Recommendation for karmi**: connect **lazily per turn**. At turn start the session asks the registry for a *server snapshot* (URL, era + cached `DiscoverResult`, headers or access token, catalogue hash) and constructs a `StreamableHTTPClientTransport` + `Client` with `connect(transport, { prior })` (zero round trips on a modern server); the objects live for the turn and are dropped. Nothing about them is persisted except what the registry already has. The session never opens `subscriptions/listen`. On 401 mid-turn the session asks the registry to refresh (idempotent: pass the token hash it used) and retries once; on `insufficient_scope` it records the challenge on the registry and fails the call with an `isError` result telling the model that re-authorisation is required.

**SSRF guard.** The Agents `isBlockedUrl` rejects malformed URLs, `0.0.0.0`, `[::]`, `metadata.google.internal`, RFC 1918, 169.254/16, IPv6 ULA/IPv4-mapped forms, and deliberately allows loopback "for local development" [Agents-mcp-client-src][Agents-client-api]. It is applied to the registered URL only; the SDK transport follows `fetch` redirects by default (UNVERIFIED that any redirect target is re-checked), and it does not cover DNS rebinding. karmi should vendor the check, apply it at registration and again to every PRM/AS metadata URL and token endpoint the auth flow discovers (the SDK already enforces HTTPS token endpoints via `assertSecureTokenEndpoint` [MCP-client-index]), use `redirect: "manual"` on the transport's `requestInit`, and enable `global_fetch_strictly_public` so `fetch()` "will strictly route requests as if they were made on the public Internet" [W-compat-flags].

## 5. Cloudflare's own MCP client support

- **`agents` `MCPClientManager`** (`agents/mcp/client`): since 0.22.0 it "is a reusable Durable Object lifecycle capability" that "owns schema initialization, persisted HTTP and RPC connection restoration, and OAuth callback interception when installed with `Lifecycle.use()`"; "`MCPClientManagerOptions.storage` is removed — the manager receives storage from the Lifecycle it is installed on, so standalone construction with an explicit `DurableObjectStorage` is no longer supported"; installing it outside `Agent` is "experimental and may change between releases" [Agents-changelog]. `Agent` constructs `new MCPClientManager(className, "0.0.1", { env, createAuthProvider })` and `lifecycle.use(this.scheduler).use(this.mcp).use(this._webSockets)` [Agents-ctor]. Confirmed: it needs Lifecycle. Tools surface to the AI SDK as `tool_${serverId without hyphens}_${toolName}` with `isError` converted to a thrown `Error` [Agents-mcp-client-src]. Transport `"auto"` tries streamable-http then SSE on 404/405/Not-Implemented [Agents-conn-src]. It also ships an x402 payment wrapper and an RPC transport for DO-to-DO MCP [Agents-pkg][Agents-mcp-client-src]. `agents/mcp/do-oauth-client-provider` is a separate export [Agents-pkg].
- **`@cloudflare/codemode` 0.5.1** (deps `acorn`, `@types/json-schema`): generates "one typed sandbox method for each discovered MCP tool" from an `McpConnector` fed by the Agents client and executes model-written code in a Dynamic Worker [Codemode-npm][Codemode-mcp]. Orthogonal to consumption; relevant to a later Capability.
- **AI Gateway**: the docs index lists no MCP feature (no `mcp` URLs; the "unified" pages are Unified Billing and the OpenAI-compatible chat endpoint) [AIG-llms]. There is no gateway-side MCP tool calling to reuse.
- **MCP Server Portals** (Zero Trust): aggregate "up to 40 MCP servers per portal" behind one `/mcp` endpoint gated by Cloudflare Access OAuth (service tokens for machine-to-machine), proxying tool calls upstream with stored credentials, and "supports stateless MCP 2026-07-28 and earlier 2025 Streamable HTTP" [CF-portals]. From karmi's side a portal is just another remote server with Access-issued bearer auth — a good default recommendation for enterprise Scopes, not something to embed.
- **`@cloudflare/workers-oauth-provider` 0.10.3**: "implements the provider side of the OAuth 2.1 protocol", KV-backed; it "contains no client-side OAuth implementation" [WOP-readme][WOP-npm]. Not reusable here.

**Reusable when building beside**: the `DurableObjectOAuthClientProvider` storage layout and state/verifier binding (MIT, vendor with attribution), `isBlockedUrl`, the `cf_agents_mcp_servers` column set and the `server_options` persistence split (durable subset vs memory-only handlers), the draft-07 validator fallback, the dual-generation `bindMcpClient` invoker if v1 support is ever needed [Agents-oauth-src][Agents-storage-src][Agents-runtime-src][Agents-invoker-src]. Not reusable: `MCPClientManager` itself (needs `agents/lifecycle`), `getAITools` (zod conversion, AI-SDK-shaped, per-session), the callback routing (assumes `/agents/{class}/{name}`).

## 6. Provider-side MCP (Anthropic MCP connector)

Beta header `mcp-client-2025-11-20`; request param `mcp_servers: [{ type: "url", url, name, authorization_token? }]` (URL "must start with https://", each server "must be referenced by exactly one MCPToolset") plus `tools: [{ type: "mcp_toolset", mcp_server_name, default_config?: { enabled, defer_loading }, configs?: { [tool]: {...} }, cache_control? }]` giving allow-list, deny-list and per-tool `defer_loading` for the Tool Search tool; "only tool calls are currently supported"; "supports both Streamable HTTP and SSE transports"; responses carry `mcp_tool_use { id, name, server_name, input }` and `mcp_tool_result { tool_use_id, is_error, content }` blocks; "API consumers are expected to handle the OAuth flow and obtain the access token prior to making the API call, and to refresh the token as needed"; works in the Batches API; "not covered by ZDR"; available on the Claude API, Claude Platform on AWS and Microsoft Foundry (beta), "not available on Amazon Bedrock, Google Cloud" [AN-mcp]. Through AI Gateway the provider-native Anthropic route passes the request body through, but `anthropic-beta` passthrough is UNVERIFIED [PS §2.2]. The Anthropic SDK also ships client-side helpers (`mcpTools`, `mcpMessages`, `mcpResourceToContent`) for the harness-side path, documented against `@modelcontextprotocol/sdk` 1.x [AN-mcp].

What the Harness loses with the connector: no per-call permission gate or hook (the call happens inside the model turn on Anthropic's side); no annotation-based read-only/parallel gating; no karmi tool-result shaping or truncation; Scope tokens are shipped to Anthropic on every request and retained under standard policy; tool names are Anthropic's, not karmi's `server__tool`; catalogue changes are invisible to karmi's prompt-cache versioning; the feature is beta, Anthropic-only and unavailable on Bedrock/Vertex, so it cannot be the seam's default [PS].

**Decision**: the Harness-side client is the default. A per-server `execution: "provider"` opt-in maps the server to `mcp_servers` + `mcp_toolset` only on the Anthropic adapter (the seam already carries `mcpServers` in provider options [PS §4]); the registry still owns the token and the allow-list; the adapter must reject the option on other providers. Justification: the connector is the one thing in this note that bypasses the Harness's own loop, and [HB] made per-tool gating and hooks core; the opt-in exists for latency-sensitive, read-only public servers where an extra network hop per call matters.

## 7. Constraints on karmi's Tool primitive

1. **JSON Schema is the native schema type.** `Tool.inputSchema` must accept a raw JSON Schema object (2020-12 default, `$schema` honoured) and pass it to providers verbatim; zod/Standard Schema is a convenience layer that *produces* JSON Schema, never the storage format. `outputSchema` optional [MCP-tools-2026][AN-define-tools].
2. **Result shape** is `{ content: Block[], structuredContent?: unknown, isError?: boolean }` with blocks `text` | `image` | `audio` | `resource_link` | `resource`; the Anthropic adapter maps `image` to base64 image blocks and everything unrenderable to text; `structuredContent` is preserved for hooks/logs but text is what the model sees [MCP-tools-2026][AN-handle-tools][PS §3].
3. **Annotations → gating**: `readOnlyHint && !destructiveHint` ⇒ parallel-safe; `destructiveHint !== false` (the default) ⇒ serialised and permission-gated; `idempotentHint` ⇒ retry-safe; `openWorldHint` ⇒ surfaced to hooks. Annotations from servers not marked trusted in Scope config are ignored (treated as destructive) [MCP-tools-2026][HB].
4. **Naming**: model-facing name is `${serverSlug}__${toolName}` sanitised to `[a-zA-Z0-9_-]`, truncated to 64 characters with a hash suffix on collision or overflow; the mapping back to `(serverId, originalName)` is stored on the Tool, never re-derived, because MCP names may be 128 chars and contain `.` [MCP-tools-2026][AN-define-tools].
5. **Catalogue versioning**: the resolved tool list for a turn carries a `catalogVersion` (hash of ordered definitions) so the Harness can keep the Anthropic `tools` prefix byte-stable across turns and only bust the prompt cache when the catalogue actually changed [AN-caching][MCP-tools-2026].
6. **Async tool sources**: the primitive needs a `ToolSource` interface (`resolve(scope, session): Promise<Tool[]>`) evaluated at turn start, because MCP tools are discovered, paginated, cached and may change; `execute` must be async and receive an `AbortSignal` [MCP-caching].
7. **Per-Scope enable/allow-lists**: registry config per server: `enabled`, `allowedTools`, `deniedTools`, `trustAnnotations`, `execution: "harness" | "provider"` — the same shape the connector's `mcp_toolset` expresses, so one config drives both paths [AN-mcp].
8. **Error taxonomy**: distinguish tool execution errors (`isError`, shown to the model) from protocol/transport/auth errors (retry, refresh, re-list, or fail the call with a Harness-authored message) [MCP-tools-2026].
9. **Header mirroring**: the Tool must keep the original `inputSchema` (with `x-mcp-header`) so the transport can emit `Mcp-Param-*`; the SDK does this from the cached `tools/list`, which is another reason the client must be fed the registry's catalogue [MCP-http-2026][MCP-client-http].
10. **Parallelism budget**: the Harness's parallel executor must cap concurrent outbound calls below the six-connection limit [W-limits].

## 8. Recommendation (v0)

1. Depend on **`@modelcontextprotocol/client` 2.0.0** (pin exactly, as Agents does) and `@modelcontextprotocol/core`; do not depend on `sdk` 1.x. Reasons: it implements the current spec and dual-era fallback, its root entry is fetch-only with a `workerd` export condition and `@cfworker/json-schema` validator, its dependency list is a fraction of 1.x (no express/hono/ajv), and 1.x is in a six-month maintenance window [MCP-client-pkg][MCP-ts-readme]. Use `versionNegotiation: { mode: "auto" }` and persist the era verdict per server.
2. Ship the **`McpRegistry` Durable Object, one per Scope** (id = Scope key), owning: server configs, allow/deny lists, static headers, OAuth client information keyed by issuer, tokens, PKCE/state rows, discovery/era cache, and the tool catalogue cache. It is the only object that talks to authorization servers.
3. Sessions never store MCP credentials. At turn start they RPC `registry.snapshot(serverIds)` and receive per-server `{ url, era, discover, authorization: { type: "bearer", token, expiresAt } | { type: "headers", headers }, catalog, catalogVersion }`; on 401 they RPC `registry.refresh(serverId, usedTokenHash)`.
4. **Connection strategy**: lazy, per turn, per server: `new Client(...)` + `StreamableHTTPClientTransport(url, { fetch, requestInit: { redirect: "manual" }, authProvider: snapshotProvider })`, `connect(transport, { prior })`; no `subscriptions/listen`; transport `"auto"` fallback to SSE only for legacy servers; drop objects at turn end.
5. **Caching**: registry stores each `tools/list` page result with `ttlMs`/`cacheScope`; refresh when stale at turn start, on `-32602` from `tools/call`, or on admin request; never background-poll. `catalogVersion` feeds prompt-cache stability.
6. **Auth**: implement `OAuthClientProvider` over registry SQLite following the Agents key layout; register via CIMD by default (karmi hosts `https://{host}/.well-known/karmi-client.json` with the single callback redirect URI; `private_key_jwt` key from Secrets Store), DCR fallback, static pre-registration per server as config. One callback route `GET /mcp/oauth/callback` in the front Worker; `state = {scopeId}.{nonce}.{serverId}`, routed to the Scope's registry which validates nonce and 10-minute expiry, validates `iss`, exchanges the code with PKCE and the `resource` parameter, then redirects to a Scope-configured URL.
7. **Static bearer / API key** headers are first-class server config and the expected common case; OAuth is opt-in per server.
8. **Tool primitive** changes per section 7: JSON Schema native, `content[]` + `isError` results, annotation gating, `server__tool` naming with 64-char sanitisation, `ToolSource` resolved at turn start, per-Scope allow-lists.
9. **Default execution is Harness-side**; `execution: "provider"` per server enables Anthropic's `mcp-client-2025-11-20` connector on the Anthropic adapter only, with the registry still supplying the token and allow-list.
10. **Vendor from `cloudflare/agents` (MIT, with NOTICE attribution)**: `isBlockedUrl` and the IPv4/IPv6 helpers; the OAuth storage-key scheme, state/verifier binding and expiry logic from `do-oauth-client-provider.ts` (re-implemented on SQLite without `AsyncLocalStorage`); the `server_options` durable-subset split; the draft-07 validator wrapper. Nothing from `MCPClientManager` or `getAITools`.
11. **SSRF**: registration-time and discovery-time URL checks, manual redirects, `global_fetch_strictly_public` in the wrangler template.
12. **Deferred**: sampling (deprecated in spec), elicitation (declare no capability; surface `input_required` as an error), x402, stdio and local servers (no subprocesses on Workers [RC]), MCP Apps/UI extension, tasks extension, RPC transport between DOs, MCP Server Portals as a managed option, revocation (RFC 7009 is not in the MCP spec).

## 9. Open questions

1. CIMD adoption in the wild: which public MCP authorization servers advertise `client_id_metadata_document_supported` today, and does karmi need a pre-registered `client_id` table for the big ones (GitHub, Atlassian, Notion)? Needs a survey ticket.
2. Access-token handout to sessions: pass the raw bearer over DO RPC (in-process, but logged?) versus having the registry proxy `tools/call` (no token leaves the registry, but every call becomes two hops and the registry's six-connection window becomes the Scope-wide bottleneck). Measure before deciding.
3. Multi-user Scopes: if a Scope is a workspace with many humans, MCP consent is per human, not per Scope; does the registry key tokens by `(serverId, principal)` and does `cacheScope: "private"` then require per-principal catalogues?
4. Legacy `Mcp-Session-Id` reuse across sessions in a Scope: a server that binds state to the session id would see one karmi Scope as one client; is sharing the id across sessions acceptable, or does each session need its own legacy session?
5. `insufficient_scope` step-up UX: which Channel surfaces the re-authorisation URL, and how does the session learn the flow completed (poll registry vs. registry-to-session notification)?
6. Does `@modelcontextprotocol/client`'s `fetch` injection let karmi run the transport through an AI Gateway or Outbound Worker for egress logging without breaking SSE streaming? Needs a spike.
7. Prompt-cache impact of catalogue churn across many servers: should `catalogVersion` be per server (so one server's change only reorders its slice) and tools be emitted grouped by server in a stable order?
8. Whether to expose MCP `prompts` and `resources` at all in v0 (Anthropic's connector does not; the Agents SDK does).
9. AI SDK `jsonSchema()` vs Anthropic `input_schema` parity for 2020-12 keywords (`$defs`, `$ref`, `oneOf`) — which keywords does Anthropic's strict mode reject? UNVERIFIED here.

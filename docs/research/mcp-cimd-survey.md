# CIMD, DCR and pre-registration among public MCP authorization servers: what karmi's client-identity chain meets in practice

Research note, 2026-08-30, answering GitHub issue #30 (child of map #1). Primary sources only: live `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server` and `/.well-known/openid-configuration` documents fetched with `curl` on 2026-08-30 from 24 public MCP servers and their authorization servers (raw JSON quoted below; hosts drift, so every table row carries the date); the MCP specification at modelcontextprotocol.io (current revision 2026-07-28); `draft-ietf-oauth-client-id-metadata-document` -00 (2025-10-08, the revision the spec pins) and -02 (2026-07-06, current); the `modelcontextprotocol/typescript-sdk` repository (`main`, commit `70de0c8`, 2026-08-28; `@modelcontextprotocol/client` 2.0.0); the `cloudflare/workers-oauth-provider` repository (`main`, commit `742e222`, 2026-08-19; 0.10.3, npm 2026-08-10); the `cloudflare/agents` repository (`main`, commit `8ffb3ad`, 2026-08-28; 0.22.0); the `cloudflare/mcp-server-cloudflare` repository (`main`, commit `08d7436`, 2026-08-24); the official MCP registry API (`registry.modelcontextprotocol.io/v0/servers`, 1,200 servers paged on 2026-08-30); vendor developer docs (GitHub, Google, Slack, Stripe, Vercel, Supabase, Linear, Atlassian, HubSpot, Cloudflare One) and platform.claude.com / code.claude.com. Source was read from shallow clones in `/tmp`; line numbers will drift. Every claim carries a bracket key from section 8; anything not verifiable from a primary source is marked UNVERIFIED. Glossary (Deployment, Scope, Connection, Catalogue, Platform) follows `CONTEXT.md`; prior decisions are cited as [P21] (MCP registry contract: pre-registered `clientId` → CIMD → DCR, one deployment-level document at `https://{host}/.well-known/karmi-mcp-client.json`) and [MC] (mcp-consumption note).

Date-sensitive: the spec deprecated Dynamic Client Registration in 2026-07-28 (PR #2858) with earliest removal "first revision released on or after 2027-07-28" [MCP-deprecated]; the spec still pins CIMD draft **-00** while the IETF draft is at **-02** [MCP-client-reg][CIMD-dt]; GitHub changed callback-URL matching on 2026-08-03 (wildcard matching is now opt-in for new apps) [GH-app-callback]; `workers-oauth-provider` 0.10.2/0.10.3 (2026-08) reworked CIMD validation and grant revocation [WOP-changelog].

## 1. Summary and recommendation

**Recommendation: do not ship karmi-owned OAuth apps or secrets. Ship (a) the deployment-level CIMD document, (b) DCR fallback that stores the issued `client_secret` per issuer, and (c) a small data table of "pre-registration required" authorization servers (keyed by AS `issuer`, no secrets) that a `doctor` check turns into a per-Deployment registration checklist.** The empirical picture behind this:

1. **CIMD is real but minority.** Of 24 servers probed, 7 authorization servers advertise `client_id_metadata_document_supported: true` — Atlassian (`auth.atlassian.com`, root and tenant issuer), Notion, Linear, Sentry, Canva, Hugging Face and Cloudflare's main API server `mcp.cloudflare.com`; 3 advertise `false` explicitly (Cloudflare `bindings`, PayPal, Square) and 14 omit the key [§2]. Every server that advertises CIMD also still exposes a `registration_endpoint`, so CIMD never widens reach today; it only changes *how* karmi identifies itself where both exist. The MCP spec makes CIMD a SHOULD with priority "pre-registered → CIMD (if advertised) → DCR (if `registration_endpoint`) → prompt the user", and the SDK gates exactly on `client_id_metadata_document_supported === true` [MCP-client-reg][MCP-client-auth].
2. **DCR still carries the ecosystem.** 18 of 24 authorization servers expose `registration_endpoint` (Atlassian, Notion, Linear, Cloudflare ×2, Stripe, Sentry, Canva, PayPal, Intercom, Asana, Hugging Face, Vercel, Supabase, Figma, Square, Jam, monday, Zapier). It is Deprecated in 2026-07-28 but eligible for removal only from 2027-07-28 [MCP-deprecated]; the SDK's `registerClient` is `@deprecated` yet functional [MCP-client-auth].
3. **Four majors require pre-registration and a client secret: GitHub, Slack, Google, HubSpot.** None has `registration_endpoint` or CIMD. GitHub: "Dynamic Client Registration is NOT supported by Remote GitHub MCP Server", "Each MCP host application needs to configure a GitHub App or OAuth App", and `client_secret` is "Required" at the token endpoint for both app kinds [GH-host-int][GH-remote-readme][GH-oauth-apps][GH-app-token]. Slack: "MCP clients must be backed by a registered Slack app with a fixed app ID", confidential OAuth with `client_id`+`client_secret`, "Only directory-published apps or internal apps may use MCP" [SL-docs]; its AS lists only `client_secret_post` [SL-live]. Google: "Google and Google Cloud remote MCP servers don't support Dynamic Client Registration or OAuth Client ID Metadata Documents"; the OAuth client is created in the Google Cloud console with exact redirect URIs [GG-cloud-auth][GG-workspace]. HubSpot: no `registration_endpoint`, `client_secret_post` only, a "user-level application" is created in the developer portal [HS-live][HS-docs]. Vercel is a fifth, softer case: it has a `registration_endpoint` but "only supports AI clients that have been reviewed and approved by Vercel" [VC-live][VC-docs].
4. **A framework-owned app cannot satisfy those four.** Each requires a *confidential* client whose secret would have to ship in karmi's package — the same credential in every Deployment, public by construction (GitHub's own stdio server, which bakes in a secret, says it "is **not truly confidential** — PKCE is what secures the flow" [GH-oauth-login]) — and an exactly registered redirect URI per Deployment host (Slack, Google, HubSpot, GitHub Apps created after 2026-08-03 and any GitHub app without wildcard matching; a GitHub App holds at most 10 callback URLs [GH-app-callback]). Slack additionally forbids unlisted apps, and Google's consent screen names the app owner. The party the user consents to must be the Platform (or the Deployment owner), not the Framework [P21 §6 keeps a per-Scope `clientId` override for exactly this]. Ownership of revocation, quota, abuse reports and ToS follows the app; karmi cannot hold it.
5. **CIMD's shape fits karmi's one-callback Deployment exactly.** A CIMD `client_id` is portable across authorization servers, needs no registration round-trip, and must list the single exact `redirect_uri`; it forbids symmetric secrets (`none` or `private_key_jwt` only) [CIMD-00 §4.1][CIMD-02 §4.1]. 13 of the 18 DCR servers accept `token_endpoint_auth_method: "none"`, and every CIMD-advertising server except Hugging Face does; Hugging Face advertises CIMD while listing only `client_secret_basic`/`client_secret_post` — whether it accepts a CIMD client with `none` is UNVERIFIED [HF-live]. `workers-oauth-provider` only implements `none` for CIMD clients [WOP-readme], so karmi's document should declare `none` in v0 and add `private_key_jwt` + `jwks` later.
6. **Where DCR issues a secret, karmi must keep it.** Supabase, Figma, Vercel, monday and Hugging Face list no `none` method; a DCR registration there returns a `client_secret` that `mcp_clients` (per issuer, [P21]) stores encrypted. This is already in the design.
7. **Discovery is messier than the spec.** Atlassian's legacy `/v1/mcp` returns 401 with no `resource_metadata` and no PRM at any well-known path, while `/v1/mcp/authv2` has a PRM naming a tenant-specific issuer `https://auth.atlassian.com/<id>` reachable only via RFC 8414 path insertion; Intercom and Zapier 401s omit `resource_metadata` (Zapier's PRM exists only at the path-inserted location); GitHub's OpenID document lacks `code_challenge_methods_supported` while its RFC 8414 document has it — and the spec says a client "MUST refuse to proceed" when the field is absent [MCP-sec-2026] — so karmi must try RFC 8414 before OIDC, implement path insertion, and fall back to root-then-path PRM when the challenge carries no `resource_metadata` [§2 notes].
8. **Anthropic hosts nothing karmi can point at.** The MCP connector expects the *caller* to "handle the OAuth flow and obtain the access token" and passes `authorization_token` through; the "remote MCP servers" page is a third-party list "not owned, operated, or endorsed by Anthropic" [AN-mcp][AN-remote]. The only "Anthropic-hosted connectors" are claude.ai-internal (Microsoft 365, Gmail, Google Calendar) and exist precisely because "the upstream identity provider only accepts the redirect URL that claude.ai registered" [CC-mcp] — Anthropic itself pre-registers per product with Google and Microsoft, which is the same conclusion as (4). The official MCP registry lists none of the 20 vendor hosts surveyed (1,067 remote entries across 223 hosts, 671 of them from one host) [REG].

What follows for karmi (§7 has the concrete shapes): keep [P21 §6]'s order; publish `https://{host}/.well-known/karmi-mcp-client.json` with `token_endpoint_auth_method: "none"`, exact single `redirect_uris`, `client_id` string-equal to its URL, served as 200 JSON under 5 KB with `Cache-Control`; DCR with `application_type: "web"` and secret storage per issuer; a `preRegistration` table (`issuer → { registerAt, secretRequired, redirectPolicy, notes }`) that `doctor` consults whenever AS metadata has neither CIMD nor `registration_endpoint`, failing the Deployment config with the vendor's registration URL and the exact callback to paste. The SDK's `Incompatible auth server: does not support dynamic client registration` becomes a typed Deployment-config error, never a user-facing `approval.requested`.

## 3. What the spec says (2026-07-28)

- **Priority** (SHOULD): "1. Use pre-registered client information for the server if the client has it available 2. Use Client ID Metadata Documents if the Authorization Server indicates that it supports them (via `client_id_metadata_document_supported` …) 3. Use Dynamic Client Registration as a fallback if the Authorization Server supports it (via `registration_endpoint` …) 4. Prompt the user to enter the client information if no other option is available" [MCP-client-reg]. Clients "SHOULD check for this capability and MAY fall back to Dynamic Client Registration or pre-registration if unavailable".
- **CIMD**: clients and servers "SHOULD support" it; pinned to draft **-00**. Client MUSTs: host at HTTPS; "`client_id` URL MUST use the "https" scheme and contain a path component"; document "MUST include at least … `client_id`, `client_name`, `redirect_uris`"; `client_id` "matches the document URL exactly"; MAY use `private_key_jwt` with JWKS. AS MUSTs: validate `client_id` equals URL; "MUST validate redirect URIs presented in an authorization request against those in the metadata document"; SHOULD cache per HTTP headers; MAY apply domain trust policies. "Client IDs based on Client ID Metadata Documents are portable across authorization servers … No re-registration is needed when the authorization server changes" [MCP-client-reg].
- **Pre-registration** (SHOULD support): hard-code a client ID "(and, if applicable, client credentials)" or "Present a UI to users that allows them to enter these details" [MCP-client-reg].
- **DCR**: "Dynamic Client Registration is deprecated. New implementations should use Client ID Metadata Documents instead"; MAY support; clients "MUST specify an appropriate `application_type`" (`web` for "remote browser-based applications served from a non-local host"); MUST handle registration failures on redirect constraints [MCP-client-reg]. Registry row: deprecated in `2026-07-28` via PR #2858, migration path CIMD, earliest removal "First revision released on or after 2027-07-28" [MCP-deprecated].
- **Issuer binding** (SEP-2352): pre-registered or DCR credentials "MUST" be keyed by AS `issuer`; on AS change "MUST NOT reuse" and "MUST re-register"; mismatched pre-registered credentials "SHOULD surface an error" [MCP-client-reg].
- **Security**: "All redirect URIs MUST be either `localhost` or use HTTPS"; "Authorization servers MUST validate exact redirect URIs against pre-registered values"; clients "MUST use the `S256` code challenge method" and "MUST refuse to proceed" when `code_challenge_methods_supported` is absent from either metadata form; CIMD: AS "SHOULD display additional warnings for `localhost`-only redirect URIs", "MUST clearly display the redirect URI hostname", "MAY implement domain-based trust policies" [MCP-sec-2026]. `resource` (RFC 8707) is MUST on authorization and token requests regardless of AS support [MCP-auth-2026].

## 4. What the CIMD draft requires

- **-00 (2025-10-08, pinned by MCP)** [CIMD-00]: §3 "Client identifier URLs MUST have an 'https' scheme, MUST contain a path component, MUST NOT contain single-dot or double-dot path segments, MUST NOT contain a fragment component and MUST NOT contain a username or password." §4.1 `client_id` "MUST match the URL of the document using simple string comparison"; `token_endpoint_auth_method` "MUST NOT include `client_secret_post`, `client_secret_basic`, `client_secret_jwt`, or any other method based around a shared symmetric secret". §5 AS metadata `client_id_metadata_document_supported`: "OPTIONAL. Boolean value". Redirect URIs: RFC 9700 exact match.
- **-02 (2026-07-06, current)** [CIMD-02][CIMD-dt]: adds "SHOULD NOT contain a query component", "/" path "NOT RECOMMENDED"; `client_secret`/`client_secret_expires_at` "MUST NOT be used"; private key material "MUST NOT be included" (public keys only via `jwks`/`jwks_uri`); AS "MUST NOT automatically follow HTTP redirects when fetching"; HTTP 200 required; SSRF: "MUST NOT fetch … URLs that resolve to special-use IP addresses", loopback relaxation only outside production; "recommended maximum size to read is 5 kilobytes"; caching "SHOULD respect HTTP cache headers", MAY bound them, "MUST NOT cache error responses" or invalid documents; AS "MAY impose restrictions or relationships between `redirect_uris` and `client_id`". Changes since -01: metadata-change security considerations, dual-registration guidance, HTTP 200 requirement, stronger SSRF text.
- Neither revision requires `client_name` or `redirect_uris` in the document itself; MCP adds them [MCP-client-reg]; `workers-oauth-provider` enforces "Non-empty `client_name` and `redirect_uris` fields, as MCP requires" [WOP-readme].

## 5. SDK and Cloudflare client/provider behaviour

**`@modelcontextprotocol/client` 2.0.0** — `packages/client/src/client/auth.ts`, `auth()` (~1014) → `authInternal()` (~1074); selection at ~1229–1285 [MCP-client-auth]:
1. `provider.clientInformation(ctx)` is read first and passed through `discardIfIssuerMismatch` (SEP-2352); a static provider (no `saveClientInformation`) with a stamped different issuer throws `AuthorizationServerMismatchError`. Any returned information short-circuits both CIMD and DCR — this is the pre-registered path.
2. Otherwise `const supportsUrlBasedClientId = metadata?.client_id_metadata_document_supported === true;` and `shouldUseUrlBasedClientId = supportsUrlBasedClientId && clientMetadataUrl`; if true, `clientInformation = { client_id: clientMetadataUrl, issuer }` (comment "SEP-991: URL-based Client IDs") and it is saved. `clientMetadataUrl` must pass `isHttpsUrl` — `url.protocol === 'https:' && url.pathname !== '/'` — else `OAuthError(InvalidClientMetadata, 'clientMetadataUrl must be a valid HTTPS URL with a non-root pathname')`; `validateClientMetadataUrl()` is exported for constructors.
3. Else DCR: throws `'OAuth client information must be saveable for dynamic registration'` without `saveClientInformation`, then `registerClient()` — `@deprecated` ("deprecated as of protocol version 2026-07-28 (SEP-2577) … Remains functional during the deprecation window (at least twelve months)") — which throws `'Incompatible auth server: does not support dynamic client registration'` when `metadata.registration_endpoint` is missing.
4. There is **no** "prompt the user" step (spec step 4); the error surfaces to the caller. `OAuthClientProvider.clientMetadataUrl?: string` is documented as "External URL the server should use to fetch client metadata document".

**Cloudflare Agents 0.22.0** — `DurableObjectOAuthClientProvider` sets `clientMetadata` to `redirect_uris: [this.redirectUrl]`, `token_endpoint_auth_method: "none"` and never sets `clientMetadataUrl`, so its clients always DCR; `addMcpServer` accepts an optional pre-registered `clientId` persisted in `cf_agents_mcp_servers.client_id` [Agents-oauth-src][Agents-mcp-client-src]. No `CIMD` string appears in the package or its CHANGELOG.

**`@cloudflare/workers-oauth-provider` 0.10.3** (provider side, i.e. what karmi would meet on Cloudflare-built servers) [WOP-src-provider][WOP-src-meta][WOP-readme][WOP-changelog]: CIMD landed in PRs #127/#129 and became opt-in in 0.3.0 (#158, `clientIdMetadataDocumentEnabled`, default `false`); metadata advertises `client_id_metadata_document_supported: !!this.options.clientIdMetadataDocumentEnabled && this.hasGlobalFetchStrictlyPublic()`, and a module-load warning says "CIMD … is disabled: add '"compatibility_flags": ["global_fetch_strictly_public"]'". Validation (`validateClientIdentifierUrl`): absolute HTTPS, no userinfo, no fragment, path required, no `.`/`..` segments, raw-path parsing; documents "must not contain client secrets" or private JWK material; 5 KB (`CIMD_MAX_SIZE_BYTES`), 10 s timeout, Cache API with 7-day cap; "The provider currently implements only `none`" for CIMD clients — `private_key_jwt`-only documents are rejected; 0.10.3 scopes default grant revocation to the redirect URI because "A CIMD client_id is the metadata document URL shared by every installation of the client". `mcp-server-cloudflare` pins 0.10.3 via `pnpm-workspace.yaml` catalog; the live split (`mcp.cloudflare.com` true, `bindings` false) shows the flag is set per app; the repo contains no `clientIdMetadataDocumentEnabled` string, so where it is set is UNVERIFIED [CF-mcp-repo].

**Claude clients** (for comparison): Claude Code supports DCR, "servers that use a Client ID Metadata Document (CIMD) … discovers these automatically", and `--client-id --client-secret --callback-port` for servers that answer "does not support dynamic client registration" — "register an OAuth app through the server's developer portal first" [CC-mcp]; claude.ai custom connectors expose "Advanced settings" for a client ID and secret [CL-connectors].

## 7. Implications for karmi

1. **Identity chain unchanged, one addition.** Order stays pre-registered `clientId` (Scope override, then Deployment) → CIMD when `client_id_metadata_document_supported === true` → DCR when `registration_endpoint` → **`PreRegistrationRequired`** error naming the issuer and the row from the §6 table. Never "prompt the user" inside a Thread; this is Deployment configuration.
2. **The CIMD document** at `https://{host}/.well-known/karmi-mcp-client.json`: `client_id` equal to that exact URL (no query, no fragment, no trailing normalisation), `client_name` (Deployment-configured), `client_uri`, `redirect_uris: ["https://{host}/mcp/oauth/callback"]`, `grant_types: ["authorization_code","refresh_token"]`, `response_types: ["code"]`, `token_endpoint_auth_method: "none"`; served `200 application/json`, under 5 KB, with `Cache-Control: max-age` (WOP caps at 7 days), no redirects, publicly reachable (not behind Access), and treated as **immutable identity** — changing the URL changes the client, and some providers scope grants by redirect URI [WOP-changelog]. `private_key_jwt` + `jwks` is a later addition (WOP rejects `private_key_jwt`-only documents today).
3. **DCR fallback** sends `application_type: "web"`, `token_endpoint_auth_method: "none"` preferred, and stores whatever comes back (including `client_secret` from Supabase/Figma/Vercel/monday/Hugging Face) in `mcp_clients` keyed by `issuer` [P21].
4. **`doctor` check**: for every configured OAuth MCP server, fetch PRM → AS metadata (RFC 8414 first, path insertion for path-form issuers, then OIDC), require `code_challenge_methods_supported ∋ S256`, and if neither CIMD nor `registration_endpoint` is present, require a `clientId` for that issuer or fail with the §6 instructions. Warn when the AS lists no `none` method and no `clientSecret` is configured (DCR will issue one; fine) and when Vercel-style allowlists apply.
5. **Discovery robustness** (from §2 notes): tolerate 401 challenges without `resource_metadata` (Atlassian legacy, Intercom, Zapier) by trying `/.well-known/oauth-protected-resource` at the resource origin, then the path-inserted form, then AS metadata at the origin; accept unquoted `resource_metadata` (Stripe); prefer RFC 8414 over OIDC for the PKCE check (GitHub).
6. **No framework-owned apps.** karmi ships no `clientId`/secret for any vendor; it ships the §6 table as data (registration URL, secret-required flag, redirect policy, notes) and documentation. A Platform that wants one-click GitHub/Slack/Google for its tenants registers *its own* app once and sets the Deployment-level `clientId`; per-Scope overrides remain for tenant-branded consent [P21 §6].
